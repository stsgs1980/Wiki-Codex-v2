Deviations from proposed split (with reasons):
- semantic-highlight-rules.ts ended at 147 lines (vs proposed ~80). Reason: 11 rules × ~6 lines per rule (in compact ternary format) + 25 lines of interfaces/JSDoc. Tried a more aggressive single-line format but it made the file unreadable and risked regex typos. The compact ternary form (`return m ? {spans: [...], next: ...} : null`) is the right balance — each rule is still scannable, all regexes are preserved verbatim, and the file fits under 150. The proposed "~80 lines" was likely based on a pure-data structure that doesn't fit the env-var rule's multi-span output.
- Did NOT use a pure-data rule format (e.g. `{regex, className, tokenGroup, advanceMode}`) as implied by the brief's "Pure config/constants". Reason: the env-var rule genuinely emits TWO spans with different className from one regex match (`m[1]` → terminal-accent, `m[2]` → star). A pure-data format would require either (a) splitting env-var into two rules (breaks the "match key= then immediately match value=" sequence — the value rule would need a "previous rule was env-var-key" context flag, which is worse), (b) introducing a `compoundSpans` field that breaks the uniform data shape, or (c) using a callback per rule (which is what I did). The function-per-rule approach (`match: (s) => TokenRuleMatch | null`) is the cleanest abstraction that handles all 11 cases uniformly, keeps the rules file pure (no JSX, no React imports, no side effects — just pure functions returning data), and preserves every regex and className character-for-character.
- semantic-highlight-rules.ts uses a `done` field REMOVED from the proposed interface (only `spans` + `next`). Reason: the original comment/shebang rules terminated the line via `remaining = ''; break` — my refactor achieves the same via `next: ''` (while loop's `remaining.length > 0` check exits). No rule needs an explicit "stop tokenizing this line" flag beyond the implicit empty-`next` signal. Removing `done` keeps the interface minimal.
- For documents/cleanup: kept `DuplicateEntry` and `DuplicateGroup` interfaces in `scan.ts` (not in route.ts). Reason: route.ts no longer references these types (the body-parsing types `ScanBody`/`DeleteBody`/`CleanupBody` are the only types route.ts needs, and they stay inline). `handleScan` returns `NextResponse` so the group types are an internal implementation detail of scan.ts. This is cleaner than re-exporting them from route.ts.
- For instructions: split POST into 2 lib files (`create.ts` + `extract.ts`) rather than 1 (`create.ts` only as the brief proposed). Reason: the AI extraction mode alone is ~105 lines (system prompt + LLM call + JSON extraction + per-instruction sanitization loop); combining it with manual creation in a single `create.ts` would push that file to ~145 lines (under the limit but tight) and conflate two distinct responsibilities. The brief's "list query building with filters" doesn't match the actual code. Padding to 50 lines would be artificial. The 17-line file (including JSDoc) is the honest size.

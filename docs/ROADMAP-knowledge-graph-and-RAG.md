# Roadmap: Knowledge Graph + RAG для документации

> **Статус:** Запланировано (не начато)
> **Дата консультации:** текущая сессия
> **Триггер:** рост базы до 50-150 документов

---

## 1. Контекст и проблема

Текущая система документации (codex/wiki) содержит 4 раздела:
- Документы (11 на момент консультации)
- Инструкции (7)
- Термины (~96, привязаны к документам через `documentId`)
- Заметки (1)

При текущем масштабе (~11 документов) list + теги + полнотекстовый
поиск работают приемлемо. При росте до **50-150 документов** система
столкнётся с тремя проблемами:

1. **Поиск сломается** - `LIKE '%word%'` вернёт шум, релевантные
   документы не будут найдены, если в них нет точного совпадения строк.
2. **Структура станет невидимой** - человек не сможет удержать в голове
   150 документов и понять, как они связаны между собой.
3. **Дубликаты и "забытые" документы** - без карты связей 30% контента
   окажется "в тени", никто не будет его находить и цитировать.

## 2. Текущее состояние системы

### Что уже есть
- Prisma schema: `Document`, `Instruction`, `Term`, `Note`, `Tag`,
  `Category`
- Термин привязан к документу (`Term.documentId`)
- AI-извлечение терминов из документов (`/api/terms/parse`)
- Ручной lookup терминов EN<->RU (`/api/terms/lookup`) с LLM
- Полнотекстовый поиск по документам (SQL `LIKE`)
- Related documents (через общие теги)
- z-ai-web-dev-sdk уже интегрирован для LLM-задач

### Чего нет
- Векторных embeddings
- Семантического поиска
- Визуализации графа связей
- AI Q&A поверх базы знаний

### Sandbox vs Production
- **Sandbox:** SQLite (`file:/home/z/my-project/prisma/dev.db`)
- **Vercel production:** PostgreSQL (через `pgvector` расширение)
- Локальные изменения schema.prisma (sqlite) НЕ коммитить

## 3. Анализ технологий

### 3.1 Graphviz vs интерактивные графы

| Инструмент | Вердикт | Обоснование |
|---|---|---|
| **Graphviz (viz.js)** | НЕ рекомендуем | Статичный SVG/PNG, не интерактивный, тяжёлый для 150+ узлов |
| **React Flow** | РЕКОМЕНДУЕМ | React-native, drag/zoom, кастомные ноды, click-to-navigate, активно поддерживается |
| Cytoscape.js | Альтернатива | Зрелый, много layout-алгоритмов, но не React-first |
| vis-network | Альтернатива | Простой force-directed, но менее гибкий |
| D3 force | Альтернатива | Полный контроль, но много кода |

**Решение:** React Flow + layout через `dagre` или `d3-force`.

### 3.2 RAG: full vs lite

| Подход | Вердикт | Обоснование |
|---|---|---|
| **RAG-lite** (embeddings + cosine + LLM поверх) | РЕКОМЕНДУЕМ | Достаточно для 150 документов, простая имплементация |
| LangChain/LlamaIndex pipeline | НЕ рекомендуем | Оверкилл, добавит сложность без пропорциональной пользы |
| Отдельная vector DB (Pinecone, Weaviate) | НЕ рекомендуем | SQLite/PostgreSQL с векторным расширением хватит |
| Re-ranking models, hybrid BM25+vector | НЕ рекомендуем | На 150 документах простой vector search уже даёт ~90% качества |
| Incremental indexing с очередями | НЕ рекомендуем | Переиндексация 150 документов занимает секунды, можно синхронно |

### 3.3 Хранение embeddings

| Окружение | Решение | Объём |
|---|---|---|
| Sandbox (SQLite) | `sqlite-vec` расширение ИЛИ JSON-поле в Prisma + cosine в JS | ~1 МБ на 150 документов |
| Production (PostgreSQL) | `pgvector` расширение | то же |

**Note:** при 150 документах cosine similarity можно считать в JS
in-memory - это быстрее, чем тащить sqlite-vec в sandbox.

## 4. План внедрения (по приоритетам)

### Этап 1 - Embeddings + семантический поиск (1-2 дня)

**Приоритет:** КРИТИЧНО при 50+ документах.

**Задачи:**
1. Проверить, поддерживает ли `z-ai-web-dev-sdk` endpoint embeddings
   - Если да - использовать
   - Если нет - подключить `@xenova/transformers` (локально, модель
     `all-MiniLM-L6-v2`, 384-dim, ~23 МБ)
2. Добавить поле `embedding` в Prisma schema (Text как JSON, или
   блоб)
3. При создании/редактировании документа/термина -> генерировать
   embedding (background job или синхронно)
4. Endpoint `/api/search/semantic` -> cosine similarity top-K
5. UI: единая строка поиска с переключателем "точный / по смыслу"
6. Переиндексация всех существующих документов (одноразовая)

**Артефакты:**
- Обновлённая `prisma/schema.prisma`
- `/api/search/semantic/route.ts`
- `/api/embeddings/generate/route.ts` (для batch переиндексации)
- Хук `use-semantic-search.ts`
- Компонент `search-bar.tsx` с переключателем режима

**Критерии приёмки:**
- Поиск "как настроить деплой" находит документ "CI/CD pipeline setup"
  без слова "деплой"
- Время ответа < 500 мс на 150 документах
- Embeddings генерируются при сохранении документа автоматически

### Этап 2 - Knowledge Graph визуализация (1-2 дня)

**Приоритет:** КРИТИЧНО при 100+ документах.

**Задачи:**
1. Собрать граф связей:
   - Документ <-> Термин (через `Term.documentId`)
   - Документ <-> Документ (через общие термины)
   - Документ <-> Тег/Категория
2. Установить `reactflow` + `dagre` (или `d3-force`)
3. Компонент `knowledge-graph-view.tsx`:
   - React Flow canvas с зумом/панорамированием
   - Кастомные ноды: document (оранжевый), term (зелёный), tag (серый)
   - Layout: dagre hierarchical или force-directed
4. Интерактивность:
   - Клик по ноду документа -> переход в DocumentViewer
   - Hover -> подсветка соседей + затемнение остальных
   - Drag для перемещения нод
5. Фильтры:
   - Только документы / только термины / всё
   - По тегу
   - По категории
   - "Только изолированные" (острова без связей -> кандидаты на
     удаление или на связывание)
6. Новая вкладка "Карта знаний" в sidebar nav

**Артефакты:**
- `/api/graph/route.ts` - отдаёт { nodes, edges } JSON
- `src/components/codex/knowledge-graph/` папка:
  - `knowledge-graph-view.tsx`
  - `graph-node.tsx` (кастомный React Flow node)
  - `graph-filters.tsx`
  - `use-graph-data.ts`
- Обновлённый `sidebar-nav.tsx` - новая вкладка

**Критерии приёмки:**
- Граф рендерится за < 1 с на 150 узлах
- Зум/панорамирование плавные (60 fps)
- Клик по ноду открывает документ
- Фильтры работают
- Мобильная версия: упрощённый вид (список кластеров вместо canvas)

### Этап 3 - AI Q&A поверх RAG (0.5-1 день)

**Приоритет:** ЖЕЛАТЕЛЬНО (вишенка, не фундамент).

**Задачи:**
1. Endpoint `/api/ai/ask`:
   - Принимает вопрос пользователя
   - Семантический поиск top-5 релевантных чанков
   - Prompt в LLM: "Ответь на вопрос, основываясь на контексте. Цитируй
     источники."
   - Возвращает: { answer, sources: [{ docId, title, snippet, score }] }
2. UI: чат-панель "Спроси у базы знаний"
   - История вопросов/ответов
   - Клик на источник -> переход в документ
   - "Этот ответ был полезен?" обратная связь (опционально)

**Артефакты:**
- `/api/ai/ask/route.ts`
- `src/components/codex/qa-panel/` папка:
  - `qa-panel.tsx`
  - `qa-message.tsx`
  - `qa-sources.tsx`
- Кнопка "Спросить у AI" в header (открывает panel справа)

**Критерии приёмки:**
- Ответ содержит цитаты с ссылками на конкретные документы
- Если ответа нет в базе - LLM честно говорит "не нашёл в документации"
- Время ответа < 3 с

## 5. Что НЕ делать (избыточное)

- Полноценный LangChain/LlamaIndex pipeline
- Отдельная vector DB (Pinecone, Weaviate, Qdrant)
- Graphviz как основная визуализация (только как fallback для экспорта
  в PNG/PDF, если понадобится)
- Re-ranking models, hybrid search BM25+vector
- Incremental indexing с очередями (BullMQ, Redis)
- Custom training/fine-tuning моделей
- Real-time graph updates через WebSocket (достаточно refetch при
  изменениях)

## 6. Открытые вопросы (проверить перед стартом)

1. **Поддерживает ли z-ai-web-dev-sdk embeddings endpoint?**
   - Проверить через SDK README или исходники
   - Если нет - использовать `@xenova/transformers` (локально, бесплатно)
2. **Sqlite-vec в sandbox или JSON+JS-cosine?**
   - При 150 документах JSON+JS-cosine ~ проще и достаточно
   - При 1000+ документов - нужен sqlite-vec
3. **pgvector на Vercel Postgres**
   - Поддерживается ли на текущем тарифе?
   - Если нет - хранить как JSON и считать в JS (медленнее, но работает)
4. **Размер embedding-модели**
   - all-MiniLM-L6-v2: 384-dim, ~23 МБ - рекомендуется
   - Если z-ai даёт embeddings - какой dim и какая цена?

## 7. Порядок выполнения (рекомендация)

```
Этап 1 (embeddings + semantic search)
   |
   v
Этап 2 (knowledge graph) ---может параллельно---> Этап 3 (AI Q&A)
```

- Этап 1 - фундамент, делать первым
- Этапы 2 и 3 можно делать параллельно (через subagents), т.к. они
  независимы
- После Этапа 1 имеет смысл нагрузить систему реальными 50+ документами
  и проверить, работает ли семантический поиск как ожидается, до
  перехода к Этапу 2
